MCP Primitives

Four tools, five resources (six URIs), two prompts. Tools are model-controlled actions; resources are app-controlled fetches; prompts are user-invoked workflow templates. Strict separation per MCP spec.

Tools 4

rescore_posting

(posting_id: str) → ScoreResult

Re-score a posting against the current rubric via the configured LLM. Persists the new score row.

tag_mismatched_score

(posting_id, expected_band, reason) → AckResult

Record operator disagreement with a stored score. Feeds the tune_rubric prompt workflow.

query_postings

(filters…) → list[PostingSummary]

Filtered list of scored postings. Supports min_score, role_anchor, date_after, with pagination.

regenerate_digest

() → DigestResult

Render top-20 postings to a digest HTML file. Operator-controlled output path; no traversal vector.

Resources 6

  • scout://digest/current most recent digest HTML
  • scout://scores/history recent scoring records, default limit
  • scout://scores/history/{limit} paginated history
  • scout://rubric/current current rubric text + version
  • scout://config/scrapers synthetic scraper config (demo)
  • scout://stats/summary aggregate counts + band distribution

Prompts 2

tune_rubric

(limit: int = 20) → str

Aggregate recent tagged mismatches + current rubric into a refinement-task prompt. Each suggestion must trace to specific mismatches.

analyze_digest_trends

(limit: int = 100) → str

Build a trend-analysis prompt from recent scoring history. Observations must be backed by counts or percentages from the data.

Architecture

Three layers, two transports, one process. Provider abstraction via LiteLLM means the LLM is swappable without code change — env-var only.

Design Decisions

Each choice below has an alternative that would also have worked. The reasoning is why this one fits the constraints.

DecisionChoiceRationale
LLM abstraction LiteLLM SDK Single-user MCP doesn't need the Proxy's token-pool/routing. SDK gives provider-agnostic acompletion() via env-var model swap.
Default model ollama/qwen2.5:3b CPU-only, ~10-18 tok/s, ~120s/scoring. Self-hosted: no API costs, no data leaving the container.
Storage backend SQLite via aiosqlite Single-process workload, WAL mode for concurrency, no operator overhead. Pydantic models on read; parameterized SQL throughout.
Transport (default) stdio Process-local, no network surface, MCP-standard. HTTP is opt-in and gated by loopback bind + Bearer auth.
JSON extraction Forgiving (first {…}) Small models occasionally add markdown fences despite strict-output instructions. Pydantic validation downstream is the real correctness gate.
Error contract Single ScoringError Callers don't need to understand LiteLLM's exception hierarchy or JSON parsing modes. Stable boundary, easy to test.
Config validation At module import Fail fast on bad env. Loopback enforcement and auth-token presence checked at import time. Production never silently degrades.
Rubric versioning In-file vX.Y header Single source of truth — the rubric IS its own manifest. Parser extracts version from the file's first line. No parallel metadata to drift.

Threat Model

The security posture is shaped by who can reach the server, what they can do, and how secrets are scoped.

Trust Boundaries

  • stdio client → server. The client process is trusted (it spawned the server). MCP semantics let the client call any registered primitive. Input validation still applies — a buggy client shouldn't be able to corrupt the database.
  • HTTP client → server. Loopback-bound; only processes on the same host can connect. Bearer-token authenticated via Starlette middleware. The public reverse proxy is the operator's responsibility, not the server's.
  • Server → Ollama. Loopback HTTP. Ollama runs unauthenticated by default; acceptable because Ollama binds to 127.0.0.1 and the entire container is one trust zone.
  • Server → SQLite. Local file access. Database files owned by the mcp user, mode 0640. No external process can read the score history.

Input Validation Guardrails

  • All SQL parameterized — payloads in user input return empty results, not executed queries.
  • Allowlist enforcement on the only two non-parameterizable fields: sort_column and sort_direction.
  • Numeric range validation at the query boundary: limit, score, min_score all bounded.
  • Non-empty enforcement on operator-provided text (rationale, reason). Whitespace-only inputs rejected.
  • Pydantic schema validation on LLM responses: malformed JSON, missing fields, or out-of-range scores all fail closed.

Secret Handling

  • .env gitignored. Production env file at /etc/career-scout-mcp/env, mode 0640, owner root:mcp.
  • Loguru sink redacts known token shapes before serialization: sk-, AKIA, ghp_, xoxb-, xoxp-, glpat-, cf_, eyJ.
  • No secrets in code, no secrets in test fixtures, no secrets in CI logs (gitleaks pre-commit + CI scan).

Out of Scope

Adversarial LLM responses (prompt injection through posting descriptions) is explicitly out of scope for v0.1.0. Rationale: the model consumes text the operator chose to score; the operator already trusts the source. A future revision could sandbox the rationale field's downstream consumers.

About Career Scout

Career Scout is my private job-search scoring pipeline, running in a separate container. It runs scrapers nightly, generates a daily HTML digest, and uses LLM scoring to rank candidate postings against my rubric.

This MCP server demonstrates the pattern I'd apply to wrap that pipeline — exposing re-scoring, tagging, and digest regeneration as MCP primitives so an LLM assistant can collaborate with me on rubric refinement and posting triage. Career Scout itself stays private; this server demonstrates the architecture.
